# План разработки Итерации 2

**Проект:** request-processor — автоматизация расчёта стоимости испытаний кабельной продукции и формирования документов  
**Статус:** Планирование (с учётом комментариев пользователя)  
**Дата:** Июнь 2026  
**Цель итерации:** Сделать инструмент практически полезным для ежедневной работы с реальными входящими заявками (PDF/письма) и быстрым формированием черновиков коммерческих предложений. Улучшить гибкость расчётов и удобство управления справочником испытаний. Сохранить чистую архитектуру, расширяемость и не раздувать объём работ.

---

## Приоритеты задач (по убыванию важности для бизнеса)

1. **Генерация черновика КП (python-docx)** — сразу даёт видимый результат, который можно показывать коллегам и использовать в работе.
2. **Начало работы с PDF** — извлечение текста и марок из типичных входящих документов (письма, акты отбора, направления в ИЛ). Это основа для дальнейшей автоматизации.
3. **Поддержка нескольких `--hour` + возможность повторных испытаний одного типа** — реалистичные сценарии (испытание напряжением до/после воздействий и т.п.).
4. **Удобное управление справочником `test_items`** — одиночное и пакетное добавление/обновление испытаний в БД (прайс-лист в основном фиксированный, постоянно перезаливать Excel не нужно).

Остальное (сложная авто-логика загрузки прайса, глубокий парсинг требований из ОА) — consciously отложено, чтобы не тратить время на низкоприоритетные вещи.

## 1. Управление справочником испытаний (`test_items`)

### Почему меняем подход
Ты rightly заметил: прайс-лист в целом фиксированный, постоянно подгружать Excel излишне. Главное — удобный способ пополнять и править справочник по мере необходимости (новые методы, корректировка цен, добавление тестов из области аккредитации).

### Что реализуем

**Расширение Repository (`sqlite_repo.py`)**

Добавляем методы (с полными docstring и типизацией):

```python
def add_test_item(self, item: "TestItemCreate") -> int:
    """Добавляет новое испытание. Возвращает id. Если code уже существует — ошибка."""

def update_test_item(self, code: str, updates: dict) -> bool:
    """Обновляет поля по коду (base_cost, name, rule_type, rule_params и т.д.)."""

def get_or_create_test_item(self, code: str, defaults: dict) -> tuple[int, bool]:
    """Полезно при импорте — создаёт, если нет."""

def list_test_items(self, category: Optional[str] = None, search: Optional[str] = None, limit: int = 100) -> list[dict]:
    """Список с фильтрами. Удобно для CLI и отладки."""

def bulk_upsert_test_items(self, items: list[dict]) -> dict[str, int]:
    """Пакетное добавление/обновление. Возвращает статистику (добавлено, обновлено, ошибок)."""
```


**CLI-команды (в `cli.py`)**

```bash
# Просмотр
request-processor list-tests --category "Электрические параметры НЧ" --search "сопротивление"

# Одиночное добавление (с валидацией)
request-processor add-test-item \
    --code resistance_core \
    --name "Электрическое сопротивление ТПЖ" \
    --base-cost 400 \
    --category "Электрические параметры НЧ" \
    --rule-type fixed \
    --method "ГОСТ 7229-76"

# Пакетный импорт (простой формат Excel/CSV с обязательными колонками)

request-processor import-tests --file data/новые_испытания.xlsx --mode upsert
```

**Упрощение `load-data`**

Оставляем команду, но:
- Убираем сложную авто-логику определения `time_based` / `per_core` из Excel (или делаем её опциональной через флаг `--auto-detect-rules`).
- Основной сценарий теперь — `import-tests` для точечного пополнения.
- При первом запуске можно загрузить полный прайс один раз, дальше правим вручную через CLI.

**Результат:** Справочник полностью под контролем оператора, легко расширять без риска сломать существующие расчёты.

## 2. Улучшение расчёта: несколько `--hour` и повторные испытания

### Проблема и требование
Сейчас `--hour temp_low=48` — один. Нужно:
- Несколько разных тестов с разным временем выдержки.
- Один и тот же тест несколько раз в рамках одного расчёта (например, испытание напряжением 4 раза: базово + после каждого климатического воздействия). Каждый экземпляр — отдельная строка в `calculation_lines` с собственным `hours` / `note`.

### Реализация

**CLI (`cli.py`)**

Click поддерживает `multiple=True`:

```python
@click.option('--hour', 'hours', multiple=True, type=str, help="Например: --hour humidity=120 --hour voltage=2")
```

Парсинг в dict `{"humidity": 120.0, "voltage": 2.0}`.

Валидация:
- Если в `--tests` есть `time_based` тест, а для него нет hours — чёткая ошибка: `Для теста 'temp_low' (time_based) не указано количество часов. Используй --hour temp_low=48`
- Разрешены дубликаты в `--tests "voltage,voltage,humidity,voltage"` — создаётся 3 строки `voltage` + 1 `humidity`.
- Если для duplicated теста указан hours — применяется ко всем экземплярам этого кода (простой и понятный вариант на старте). При необходимости в будущем сделаем `voltage:1=2 voltage:2=4`.

**Обновление `cost_calculator.py`**

```python
def calculate_cost(
    mark: str,
    cores: int,
    groups: int,
    test_codes: list[str],           # может содержать дубликаты
    hours_map: dict[str, float],     # code -> hours (для time_based)
    test_items_repo: TestItemsRepository,
) -> Calculation:
    ...
    lines = []
    for idx, code in enumerate(test_codes):
        item = repo.get_test_item_by_code(code)
        if not item:
            # создаём "виртуальную" строку или ошибка (configurable)
            ...
        h = hours_map.get(code)
        if item.rule_type == "time_based" and h is None:
            h = item.rule_params.get("default_hours")
        if item.rule_type == "time_based" and h is None:
            raise ValueError(f"Для {code} не указано hours и нет default в rule_params")

        final_cost, multiplier, note = _apply_rule(item, cores, groups, h, cores_count=cores)
        lines.append(CalculationLine(... hours=h, note=note ...))
    ...
```

**Пример использования (реалистичный)**

```powershell
request-processor calculate `
    --mark "ВВГ-Пнг(А) 3х4ок(М,РЕ)-0,66" `
    --cores 3 `
    --tests "resistance_core,voltage,voltage,humidity,temp_low" `
    --hour humidity=120 `
    --hour temp_low=48 `
    --hour voltage=2
```

Результат: 5 строк в breakdown, две из них — `voltage` с одинаковыми параметрами (или разными, если позже усложним).

**Валидация на уровне CLI + калькулятора** — дружелюбные сообщения + exit code 1 при ошибке.

## 3. Работа с PDF (старт)

### Выбранная библиотека
`pdfplumber` — отлично извлекает текст + таблицы из типичных писем, актов и направлений (лучше чистого `pypdf` для наших примеров).

Добавляем в `pyproject.toml`:
```toml
dependencies = [
    ...
    "pdfplumber>=0.11.0",
]
```

### Новый модуль `pdf_extractor.py`

Чистые функции + минимальный класс-обёртка при необходимости:

```python
def extract_text(pdf_path: Path | str) -> str:
    """Извлекает весь текст из PDF (с сохранением примерно порядка)."""

def extract_tables(pdf_path: Path | str) -> list[list[list[str]]]:
    """Извлекает таблицы. Возвращает список таблиц, каждая — список строк, каждая строка — список ячеек."""

def find_cable_marks(text: str) -> list[str]:
    """Ищет марки кабелей по известным паттернам (расширяем cable_mark_parser)."""
```

**CLI**

```bash
request-processor extract-pdf \
    --pdf "attachments/Письмо на период. исп. от 04.05.26.pdf" \
    --output data/extracted/letter_2026-05-04.json \
    --show-marks
```

Выводит:
- Краткую статистику (страниц, таблиц)
- Найденные марки (с контекстом)
- Полный текст (опционально `--full-text`)

**Что именно делаем в итерации**
- Успешно обрабатываем примеры из attachments:
  - `Письмо на период. исп. от 04.05.26.pdf` (таблица марок + ТУ + пункты)
  - `27_1-2-2026 Акт отбора...pdf`
  - `27_1-2-2026 Направление в ИЛ...pdf`
- Находим марки вида `ВВГ-Пнг(А) 3х4ок(М,РЕ)-0,66`, `ККЗ МК ПвЭмлВнг(А)-LSLtx-ХЛ-2У ...` и т.д.
- Сохраняем результат в JSON (текст + найденные марки + таблицы) — удобно для следующей итерации.

**Что НЕ делаем**
- Глубокий семантический парсинг пунктов требований и автоматический маппинг на тесты из области аккредитации (это большая отдельная задача + требует знаний ОА).
- Обработку сканов низкого качества / OCR (пока предполагаем, что PDF текстовые или с хорошим текстом).

## 4. Генерация черновика КП (`python-docx`)

### Цель
По расчёту (или списку марок + выбранным испытаниям) формировать красивый, готовый к отправке черновик коммерческого предложения в формате DOCX, похожий на пример `Расчет ККЗ исх от 08.04.2026.docx` и соответствующий шаблону `Шаблон КП с объемом испытаний.docx`.

### Новый модуль `kp_generator.py`

Архитектура (лёгкая, без избыточного ООП):

```python
def generate_kp(
    calculation: Calculation,
    output_path: Path,
    customer: Optional[dict] = None,   # пока можно передавать вручную или заглушить
    template_path: Optional[Path] = None,
) -> Path:
    """Генерирует КП. Если template_path не указан — создаёт чистый профессиональный документ."""
    ...
```

Внутри:
- `build_header(doc)` — шапка с реквизитами центра (адрес, аккредитация РОСС RU.0001.21КБ32, телефон, email)
- `build_title(doc, calculation)`
- `build_summary_table(doc, calculation)` — итоговая таблица по маркам (как в примере расчёта ККЗ)
- `build_details_table(doc, calculation)` — детальный объём испытаний (из `calculation_lines`)
- `build_footer(doc)` — "Предложение действительно 30 дней", подпись, контакты, "Срок выполнения до 40 рабочих дней"

**Стили и форматирование**
- Используем `python-docx` стили + прямое форматирование (как в твоём протокольном генераторе).
- Таблицы с границами, merged cells где нужно (например, "Итого"), выравнивание.
- Числа с пробелами тысяч (1 585 000,00 ₽) — через `locale` или простой форматтер.
- НДС 22% жёстко или из конфига (пока 0.22).

**CLI**

```bash
request-processor generate-kp \
    --calculation-id 42 \
    --output "output/КП_ВВГ_3х4ок_2026-06-24.docx" \
    --customer-name "ООО «Производитель»"
```

Или удобно:
```bash
request-processor generate-kp --last --open   # открыть после генерации
```

**Расширяемость**
- Отдельные функции `build_*` — легко добавлять секции в будущих итерациях (условия оплаты, приложения с протоколами, QR и т.д.).
- Можно позже сделать `KPBuilder` класс, если появится много вариантов (КП / Заявка / Счёт).

**Тестирование**
- Генерируем на основе реального примера из `attachments/Расчет ККЗ исх от 08.04.2026.docx` и сравниваем структуру.
- Проверяем на расчётах с повторными испытаниями и разными `rule_type`.

## Что сознательно НЕ делаем в этой итерации (scope guard)

- Сложная авто-логика определения `rule_type` и `rule_params` при загрузке Excel.
- Полноценный парсинг PDF с извлечением пунктов требований и автоматическим подбором тестов из области аккредитации (ОА PDF — 360+ страниц, это отдельная большая задача).
- Веб-интерфейс / Streamlit.
- Генерация заявки на испытания и протокола (это Итерация 3).
- Обработка нескольких марок из одного PDF в один расчёт автоматически (пока пользователь копирует марки вручную в `calculate`).
- Интеграция с email / 1С / корпоративными системами.

## Ожидаемый результат после Итерации 2

Оператор сможет за 2–5 минут:
1. Получить PDF письма/акта/направления.
2. Извлечь из него марки (`extract-pdf`).
3. Посчитать стоимость с учётом повторных испытаний и реального времени выдержки (`calculate` с несколькими `--hour` и дубликатами в `--tests`).
4. Сформировать красивый черновик КП (`generate-kp`) и отправить заказчику.

Справочник испытаний легко пополнять и править без перезаливки всего прайса.

Архитектура остаётся чистой: отдельные модули под свои зоны ответственности, Pydantic-валидация, Repository, чистые функции расчёта.
