# request-processor

**Автоматизация расчёта стоимости испытаний кабельной продукции и формирования документов**

**Статус:** Итерация 1 завершена (MVP-скелет)  
**Дата:** Июнь 2026

---

## 1. Описание проекта и идея

`request-processor` — это инструмент для ускорения обработки входящих заявок на испытания кабельной продукции в испытательном центре.

### Основная идея

Оператор получает заявку (PDF, письмо, таблица), в которой указаны марки кабелей и требуемые испытания. Нужно быстро:
1. Разобрать марку кабеля.
2. Определить перечень необходимых испытаний.
3. Рассчитать стоимость с учётом всех правил прайс-листа (количество жил, группы, время выдержки в камерах и т.д.).
4. Сформировать коммерческое предложение и/или заявку на испытания.

Сейчас этот процесс занимает много времени и делается вручную в Excel. Цель проекта — максимально автоматизировать рутинную часть.

## 3. Архитектура и подход к разработке

### Общая структура (Итерация 1)

```
src/request_processor/
├── cli.py                 # Точка входа (Click)
├── models.py              # Pydantic-модели домена
├── cable_mark_parser.py   # Парсер марок кабеля
├── cost_calculator.py     # Чистая функция расчёта
├── sqlite_repo.py         # Работа с SQLite (Repository)
└── __init__.py
```

### Используемые паттерны и принципы

| Паттерн / Принцип       | Где применяется                  | Зачем |
|-------------------------|----------------------------------|-------|
| **Repository**          | `sqlite_repo.py`                 | Отделить работу с БД от бизнес-логики |
| **Pydantic модели**     | `models.py`                      | Валидация данных + удобная работа с типами |
| **Чистые функции**      | `calculate_cost()`               | Легко тестировать, не зависит от CLI и БД |
| **CLI (Click)**         | `cli.py`                         | Простой, но мощный интерфейс на старте |
| **Separation of Concerns** | Все модули                    | Каждый файл отвечает за свою зону ответственности |
| **Editable install**    | `pyproject.toml`                 | Удобная разработка без постоянной переустановки |

**Почему именно такая архитектура на старте:**
- Плоская структура (без глубоких пакетов) — проще поддерживать на первой итерации.
- Repository + Pydantic — классический и расширяемый подход для небольших инструментов.
- Чистый калькулятор — можно будет позже вынести в отдельный сервис или использовать в веб-интерфейсе.

## 4. Как это работает (механика)

### Основной поток данных

```
CLI (calculate)
   ↓
parse_cable_mark()           ← разбор марки
   ↓
get_test_item_by_code()      ← получение правил из БД
   ↓
_apply_rule()                ← применение формулы (fixed / per_core / time_based)
   ↓
Calculation (Pydantic)       ← сборка результата
   ↓
save_calculation()           ← сохранение в SQLite
   ↓
print_breakdown()            ← красивый вывод в терминал
```

### Правила расчёта (на текущий момент)

- **`fixed`** — простая стоимость (берётся `base_cost`).
- **`per_core`** — стоимость умножается на количество жил.
- **`time_based`** — `Базовая стоимость + (Стоимость часа × Количество часов)`.

## 5. Основные команды

### Инициализация

```powershell
request-processor init-db
```

Создаёт базу данных `data/app.db` и заполняет демо-данными.

### Загрузка реального прайс-листа

```powershell
request-processor load-data --price "путь\к\Обновленная стоимость на 2026 год.xlsx"
```

### Ручной расчёт (основная команда)

```powershell
request-processor calculate `
    --mark "ВВГ-Пнг(А) 3х4ок(М,РЕ)-0,66" `
    --cores 3 `
    --groups 1 `
    --tests "resistance_core,temp_low,humidity" `
    --hour temp_low=48 `
    --hour humidity=120
```

### История расчётов

```powershell
request-processor history --limit 10
```

## 6. Почему сделано именно так

- **Почему Click, а не Typer или argparse?**  
  Click — зрелый, хорошо документированный, удобен для сложных CLI с подкомандами.

- **Почему SQLite, а не PostgreSQL?**  
  На первой итерации не нужно поднимать сервер БД. SQLite отлично подходит для локального инструмента.

- **Почему Pydantic, а не dataclasses?**  
  Pydantic даёт валидацию «из коробки» и удобную сериализацию (особенно важно для сохранения `parsed_mark` в JSON).

- **Почему `--hour key=value`, а не JSON?**  
  Гораздо удобнее в PowerShell и обычном терминале. JSON оставлен только для обратной совместимости.

## 7. Структура базы данных (Итерация 1)

На текущий момент в приложении используется **SQLite** с тремя основными таблицами.

### Схема (упрощённая ER-диаграмма)

```
test_items
    │
    │ 1
    │
    └──< calculation_lines >── 1 calculations
```

### Описание таблиц

**`test_items`** — справочник испытаний (загружается из прайс-листа)

| Поле            | Тип      | Описание                                      |
|-----------------|----------|-----------------------------------------------|
| `id`            | INTEGER  | Первичный ключ                                |
| `code`          | TEXT     | Уникальный код теста (slug из названия)       |
| `name`          | TEXT     | Полное наименование испытания                 |
| `base_cost`     | REAL     | Базовая стоимость                             |
| `category`      | TEXT     | Категория (Электрические, Климатические и т.д.) |
| `method`        | TEXT     | Ссылка на метод/ГОСТ                          |
| `rule_type`     | TEXT     | `fixed` / `per_core` / `per_group` / `time_based` |
| `rule_params`   | TEXT     | JSON с дополнительными параметрами (часы, стоимость часа и т.д.) |

**`calculations`** — заголовок одного расчёта

| Поле                     | Тип      | Описание                              |
|--------------------------|----------|---------------------------------------|
| `id`                     | INTEGER  | Первичный ключ                        |
| `mark`                   | TEXT     | Исходная строка марки кабеля          |
| `parsed_mark`            | TEXT     | JSON с разобранной маркой (`CableMark`) |
| `total_cost_without_vat` | REAL     | Итого без НДС                         |
| `vat_rate`               | REAL     | Ставка НДС (0.22)                     |
| `total_cost_with_vat`    | REAL     | Итого с НДС                           |
| `source`                 | TEXT     | `manual` / `pdf`                      |
| `created_at`             | TEXT     | Дата и время расчёта                  |

**`calculation_lines`** — детальные строки расчёта (каждое испытание в рамках одного расчёта)

| Поле             | Тип      | Описание                                      |
|------------------|----------|-----------------------------------------------|
| `id`             | INTEGER  | Первичный ключ                                |
| `calculation_id` | INTEGER  | Ссылка на `calculations.id`                   |
| `test_item_id`   | INTEGER  | Ссылка на `test_items.id` (может быть NULL)   |
| `test_name`      | TEXT     | Название испытания на момент расчёта          |
| `base_cost`      | REAL     | Базовая стоимость                             |
| `multiplier`     | REAL     | Множитель (кол-во жил / групп / часов)        |
| `hours`          | REAL     | Количество часов (для time_based)             |
| `final_cost`     | REAL     | Итоговая стоимость по строке                  |
| `note`           | TEXT     | Пояснение к расчёту (например "× 3 жил")      |

### Примечания по схеме

- `rule_params` хранится в виде JSON-текста (удобно для расширения).
- На Итерации 1 связи между таблицами не жёсткие (возможны расчёты с тестами, которых уже нет в `test_items`).
- В будущем планируется добавить таблицы `requests`, `test_mappings` и `generated_documents`.
