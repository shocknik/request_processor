## 4. Установка на рабочий ПК — это и есть следующий шаг

Решение пользователя от 1 октября 2026 важнее привычного `scripts\update.ps1`.

Раньше программа жила на диске `W:` (диск сервера в домене). Серверы заменили, буква `W:` стала ненадёжной. Обновление поверх старой папки из-за этого не делаем. Новая копия — целиком на локальном диске C: рабочего компьютера.

[`docs/UPDATE.md`](UPDATE.md) по-прежнему описывает обновление поверх уже стоящей папки. Это документ **на потом**, когда `C:\Lab_request` уже работает. Для сегодняшнего переноса его не выполнять.

### Что уже случилось 1 октября 2026

Первый запуск на IDM23060 оборвался **до распаковки**. По журналу, который привезли обратно (`C:\Users\User\Downloads\Стек установки.txt` на компьютере разработки):

- диск `W:` не подключён;
- сервер ответил, база нашлась по сетевому пути выше;
- скрипт упал на проверке файла через `python -c` с кавычками (`File "<string>", line 5`) при `$ErrorActionPreference Stop`;
- папка `C:\Lab_request` **не создавалась**, старые папки **не удалялись**;
- на рабочем столе уже есть запасная копия `C:\Users\n.molchanov\Desktop\Lab_request_rescue`.

Исправление уже в локальном `поставить_на_C.ps1`: проверка базы пишется во временный файл `lab_request_db_facts.py`, ошибка Python установку не роняет. На рабочем компьютере нужно **заменить только этот скрипт** в папке набора и запустить снова. Весь архив из-за этого заново не собирать.

Перед запуском, из папки набора:

```powershell
Unblock-File -LiteralPath .\поставить_на_C.ps1
powershell -ExecutionPolicy Bypass -File .\поставить_на_C.ps1
```

Если Windows спросит «Не запускать / Запустить однажды / Приостановить», нажать **R** (один раз) и Enter. Клавиша D — это отказ.

Папку `Lab_request_rescue` **не удалять**. Это запас отдельно от программы. Если её уже стёрли, скрипт создаст папку на рабочем столе заново и снова скопирует туда привезённую базу; более ценна та копия, которую скрипт успел забрать со старого места. Её нет в наборе на флешке.

Скрипт сам не ставит и не удаляет Python и Tesseract. Нужны Python 3.10+ уже в PATH (на работе был 3.12), интернет на время библиотек и не меньше 2 ГБ свободно на C:. Места меньше — скрипт останавливается и ничего не удаляет. `C:\Lab_request` должна быть пустой или отсутствовать; иначе он откажется (можно `-Dest "C:\Lab_request2"`, но обычный путь — `C:\Lab_request`).

В конце скрипт помечает базу рабочей. В заголовке окна должно быть `[WORK]`. Команду `prepare-prod-db` **не запускать**: она оставляет прайс и стирает марки, организации и заказы.

Базу с компьютера разработки (`data\app.db` в этом репозитории, роль dev: тестовые организации, последний заказ 28.07) на рабочий ПК **не копировать**.

### Как понять, что установка прошла

1. Ярлык Lab_request на рабочем столе открывает `C:\Lab_request\start_gui.bat`, не флешку и не `W:`.
2. В заголовке есть `[WORK]`.
3. В организациях поиск «спец» или «тольят» находит знакомые карточки.
4. Заказов не меньше 23. Число больше 23 значит, что подхватилась более поздняя база со старого места — так и нужно. Число записать.
5. `Lab_request_rescue` на рабочем столе на месте.
6. Программа на месте отвечает чеклисту [`CHECKLIST_TZ70_OPERATOR.md`](CHECKLIST_TZ70_OPERATOR.md), раздел 11.

Журнал пожеланий после установки:

- залипание полей (#1) можно отметить «сделано», когда поля заказчика сами пощёлкали и окно не замерло;
- копирование марки (#2 и #13) — только когда это увидели на IDM23060;
- порядок строк письма (#12) заранее «сделано» не ставить и не писать «двойников схлопнули». Сначала разобрать живое письмо и посчитать строки.

Дальше эту копию обновляют уже поверх `C:\Lab_request` скриптом `update.ps1` из нового архива. Он базу не затирает. Сегодняшний запуск — первая установка на новое место, не такое обновление.

## 5. Чего не начинать, пока не попросят

Волна развития, в коде её нет. В один архив с установкой её не мешать. Не делать «заодно»:

- оптический кабель как модель (модули и волокна, не только склейка текста `СП-|` + `ОКС`, она уже есть);
- класс кабеля;
- недавние папки;
- копия заказа;
- суммы по группам;
- наборы ПСИ;
- коммерческое предложение без подтверждения заявки;
- семейство марок `РК 50-…`.

Также не делать без отдельной просьбы: подъём номера версии, `prepare-prod-db`, перенос `data\app.db` между компьютерами, коммит документов ТУ, правка соседнего проекта protocol_generator (сюда только JSON `export-protocol-meta`).

Если пользователь пишет «продолжим» без подробностей — спросить, речь про установку на IDM23060 или про новый кусок программы. По умолчанию волну D не открывать и на этом компьютере установщик не запускать.

```powershell
cd D:\My_projects\request_processor
.\.venv\Scripts\python.exe -m pytest tests/ -q --tb=line
.\.venv\Scripts\ruff.exe check src tests
```

После смены схемы базы — `request-processor migrate-db`, не ручной DROP.

Горячий разбор марок остаётся детерминированным: `_clean_mark` не ходит в SQLite, MarkCorrector и языковую модель. Это уже закреплено тестами, не ослаблять.

Интерпретатор — `.venv\Scripts\python.exe`. Запуск окна после правки интерфейса — новый процесс (`request-processor gui` или `start_gui.bat`). Старый `python` / `pythonw` этой программы перед проверкой закрыть.

Логи: `data\logs\app_*.log` или `%LOCALAPPDATA%\Lab_request\logs`, плюс `gui_extract_trace.log`.

Роль базы смотреть командой `request-processor db-info`. Метка `data\db_profile.local.yaml` в git не входит. База в репозитории на этом компьютере — тестовая.
